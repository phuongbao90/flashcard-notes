### Question 79217232-d00f-471b-94ba-84735150374b

- In an interview, how does an interviewer assess whether a candidate possesses genuine code ownership versus "cognitive surrender" over AI-generated code?

### Answer

- **The "Why this line?" probe**: The interviewer identifies a non-obvious line, configuration, or utility pattern generated by AI and asks: "Why did you choose this implementation over alternative approaches?"
- **Red flag behavioral signal**: "I am not sure, that's just what Cursor/Claude suggested and it worked." The candidate abdicates intellectual responsibility to the tool.
- **Green flag behavioral signal**: The candidate articulates the trade-offs, internal mechanics, and boundary conditions: "The AI suggested this pattern to handle edge case X, but I verified that it preserves Y without introducing memory leaks. An alternative would be approach Z, but that adds unnecessary complexity."
- **Core engineering principle**: Committing or presenting code means owning 100% of its consequences, bugs, security vulnerabilities, and maintenance debt, regardless of who or what generated the characters.

### Question 7dcce1b6-6d29-4cae-b2ed-a06455b0e612

- During a live assessment, an AI assistant gets stuck in a hallucination loop or generates increasingly broken code for several iterations. What behavioral response does the interviewer expect from a senior frontend engineer?

### Answer

- **Recognizing the "Sunk Cost Prompting" trap**: Weak candidates fall into an emotional doom-loop: repeatedly copying compiler errors into the prompt window without reading the terminal stack trace, hoping the next prompt miraculously resolves it.
- **Senior course correction mechanics**:
  - *Enforce a strict prompt timebox*: Stop after two failed generation attempts or 3 minutes of stalled progress.
  - *Close the AI chat and inspect the runtime*: Step back, open Chrome DevTools, inspect the network waterfall or memory tab, and trace the actual error.
  - *Consult authoritative documentation*: Check official docs (MDN, React docs) rather than arguing with an LLM about framework behavior.
  - *Pivot to manual implementation*: Write the missing logic or minimal reproduction manually to regain control.
- **Interviewer evaluation takeaway**: Demonstrates metacognitive control, emotional regulation under pressure, and knowing when AI transitions from an accelerator into a liability.

### Question edbf3d9d-76f1-4ee7-bac9-dff88226eeec

- An interviewer intentionally gives a vague, ambiguous feature request (e.g., "Build an offline-ready draft saving mechanism"). What behavioral difference in AI usage separates a junior from a staff frontend developer?

### Answer

- **Junior behavioral pattern (Immediate prompting)**: Immediately pastes the interviewer's prompt verbatim into the AI tool, generating a 200-line bloated snippet with arbitrary third-party libraries (e.g., Dexie.js) without clarifying scope, constraints, or scale.
- **Staff behavioral pattern (Domain framing and constraint isolation)**:
  - *Clarify constraints before tooling*: Proactively asks the interviewer about storage quotas, cross-tab synchronization, conflict resolution strategies (last-write-wins vs. operational transform), and fallback behavior.
  - *Architect interfaces manually*: Drafts the TypeScript state contract, storage interface, and failure boundaries before writing any implementation.
  - *Targeted delegation*: Prompts the AI only for isolated, specific subtasks (e.g., "Write a pure reducer to merge offline draft conflicts based on timestamp precedence").
- **Interviewer takeaway**: High-leverage engineers control the architecture and use AI for tactical execution, never for strategic ambiguity resolution.

### Question 812a4290-557e-4158-8082-e51541474e76

- In a behavioral interview round, a candidate is asked: "A teammate submits a 1,200-line PR that is obviously AI-generated, full of verbose boilerplate and unvetted dependencies. How do you handle this review?" What is the interviewer assessing?

### Answer

- **Assessing technical stewardship and empathy**: Evaluates whether the candidate can prevent codebase degradation ("AI slop") while maintaining collaborative, psychologically safe team dynamics.
- **Staff-level behavioral response**:
  - *Focus on cognitive load, not tool shaming*: Avoid attacking the author or the AI; focus on maintainability, readability, and the blast radius of unverified abstractions.
  - *Request batch-size decomposition*: Ask the teammate to split the 1,200-line diff into reviewable increments (e.g., types/interfaces first, business logic second, UI components third).
  - *Demand verification of edge cases*: Ask targeted questions in the PR review: "How does this hook handle concurrent network cancellation?" or "What is the bundle footprint of library X on mobile 3G?"
  - *Institutionalize systemic guardrails*: Propose team-wide standards, such as PR diff limits, automated bundle size CI gates, and prompt hygiene guidelines.

### Question 4d45f2c1-d9b3-4e24-aaf3-aa078e9d0334

- During a live coding interview where AI tools are permitted, what verbal and behavioral communication habits distinguish candidates who interview effectively with AI from those who fail?

### Answer

- **The "Silent Passenger" anti-pattern**: The candidate goes completely silent, frantically typing prompts, reading paragraphs of LLM output, and leaving the interviewer isolated and unable to evaluate their thought process.
- **Effective collaborative communication protocol**:
  - *Narrate intent before prompting*: "I am going to prompt the AI to generate a mock dataset with 10 varied edge cases so we can validate boundary handling quickly."
  - *Think aloud while reading AI output*: "The model generated a working solution, but it used `any` types and an unmemoized callback that will cause child re-renders. Let me fix those before running it."
  - *Include the interviewer in trade-off discussions*: "The assistant suggested two approaches: local state with context vs. URL search params. For this user story, URL params are superior for shareability. Do you agree?"
- **Interviewer takeaway**: High-performing candidates treat both the human interviewer and the AI as collaborators, keeping the human interviewer in the driver's seat.

### Question adf711fa-10a4-4892-a55a-a8c87d11e3fc

- An interviewer asks a candidate a complex browser-rendering question. The candidate consults an AI assistant, which produces an authoritative, persuasive, but factually incorrect explanation. What does the interviewer assess in the candidate's reaction?

### Answer

- **The Authority Bias and Sycophancy trap**: LLMs generate responses with high linguistic confidence even when hallucinating browser mechanics (e.g., claiming a non-existent CSS property exists or misrepresenting layout thrashing).
- **Behavioral assessment criteria**:
  - *Epistemic skepticism*: Does the candidate pause and critically compare the AI's explanation with fundamental browser rendering pipeline mechanics (Parse -> Style -> Layout -> Paint -> Composite)?
  - *Empirical verification*: Does the candidate write a quick 3-line browser console test or inspect the element in DevTools to verify the AI's assertion before accepting it as truth?
  - *Intellectual courage*: Can the candidate openly declare to the interviewer: "The AI is claiming X, but that contradicts how the browser handles stacking contexts. Let's verify this against MDN"?
- **Interviewer takeaway**: Verifies whether the candidate possesses grounded platform fundamentals or is easily swayed by fluent machine output.

### Question ac2800b1-e1e5-423e-ad18-f90021250f92

- When does a staff-level frontend developer deliberately choose NOT to use an AI assistant, and how does an interviewer evaluate this decision-making process?

### Answer

- **Scenarios where AI usage is counterproductive or harmful**:
  - *High muscle-memory, low-complexity tasks*: Writing standard JavaScript array methods (`map`, `filter`, `reduce`) or basic CSS grid templates is faster manually than prompting, reviewing, and context switching.
  - *Deep root-cause debugging of runtime race conditions*: AI cannot inspect live memory heaps, DevTools performance flamegraphs, or WebSocket packet waterfalls; prompting AI on runtime bugs produces superficial guesses.
  - *Bleeding-edge framework features*: Implementing newly released canary APIs where the AI's training data leads to hallucinated legacy patterns.
  - *High-consequence security/auth boundaries*: Writing token refresh mechanics or cryptographic validation where subtle hallucinated logic can expose vulnerabilities.
- **Interviewer evaluation takeaway**: Candidates who reflexively use AI for every single keystroke exhibit low tooling maturity; staff engineers treat AI as a specialized power tool, not a cognitive crutch.

### Question 934f6c65-f802-42f2-b2c3-f8f77617738c

- An engineering manager notices that feature velocity has doubled since adopting AI coding tools, but production regressions have increased by 40%. In a staff-level interview, how should the candidate propose addressing this?

### Answer

- **Diagnosing the "Artificial Velocity" illusion**: Fast code generation without deep comprehension creates an illusion of speed where time saved during authoring is repaid with compound interest during debugging, PR review bottlenecks, and production outages.
- **Staff-level systemic interventions**:
  - *Shift verification left with automated gates*: Mandate behavior-driven integration tests (Playwright, React Testing Library) and type-check gates in CI before any PR can be merged.
  - *Redefine engineering KPIs*: Stop evaluating engineering output by lines of code or PR velocity; measure DORA metrics like Change Failure Rate (CFR) and Mean Time to Restore (MTTR).
  - *Establish AI verification criteria*: Require that any AI-assisted code include a test covering edge cases and an explicit PR description explaining failure modes.
  - *Post-mortem culture*: Conduct blameless post-mortems on AI-introduced incidents to uncover shared misunderstandings of platform behavior.

- [More detail on DORA Metrics and Engineering Performance](https://dora.dev/)
- [More detail on Blameless Post-Mortem Culture](https://sre.google/sre-book/postmortem-culture/)

- How does an interviewer evaluate a candidate's adaptability to evolving AI tooling paradigms (e.g., transitioning from inline autocomplete to chat, to agentic CLI workflows like Claude Code or Cursor Composer)?
