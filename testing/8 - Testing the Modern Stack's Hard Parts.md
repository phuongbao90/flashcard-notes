# Testing the Modern Stack's Hard Parts

### Question fbf3a4ef-a793-48c3-908f-dd0d10dd3bcd

- Why can't **React Server Components (RSC)** be rendered in JSDOM via standard React Testing Library, and what is the pragmatic senior strategy to test them?

### Answer

- **The RSC rendering gap**:
  - React Testing Library (RTL) runs inside Node.js using simulated browser DOMs (JSDOM/HappyDOM) that execute client-side React (`react-dom/client`).
  - Server Components are asynchronous functions that stream React Flight payloads (`self.__next_f`) generated by the React server renderer (`react-server`).
  - JSDOM does not implement server streaming, async component rendering, or server-only module bindings (`import 'server-only'`).
- **The Pragmatic 3-Tier Strategy**:
  1. **Extract pure data/business logic into testable DAL functions**: Move SQL queries, permission checks, and payload mapping out of the Server Component into pure async functions that can be unit/integration tested in Node.
  2. **Push UI rendering to Client Components**: Keep the Server Component as an ultra-thin data orchestrator, passing data as props to a Client Component which is thoroughly tested in RTL.
  3. **Verify end-to-end via Playwright**: Test the compiled Next.js application in Playwright E2E suites to verify that the Server Component renders correctly on the server and hydrates on the client.

```tsx
// ❌ RTL cannot render this async server component directly in JSDOM:
export async function UserDashboardPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const data = await db.user.findUnique({ where: { id } }); // Fails in RTL without Node DB mocks!
  return <DashboardView user={data} />;
}

// ✅ Strategy:
// 1. Unit/integration test the Data Access Layer (DAL) in Node
describe('getUserDashboardData', () => {
  it('rejects unauthorized access and returns sanitized DTO', async () => {
    await expect(getUserDashboardData('other-tenant-id')).rejects.toThrow(/unauthorized/i);
  });
});

// 2. Integration test the presentational Client Component in RTL
it('renders user metrics dashboard', () => {
  render(<DashboardView user={{ name: 'Alice', metrics: [10, 20] }} />);
  expect(screen.getByRole('heading', { name: /alice/i })).toBeVisible();
});
```

### Question 3e44ff93-1633-407f-9fe4-f60c06be42ec

- How do you integration-test Next.js **Server Actions and Route Handlers** directly in Node, and why are Data Access Layer (DAL) **"deny tests"** mandatory?

### Answer

- **Direct Server Action testing**:
  - A Server Action is a standard async JavaScript function that runs on the server. You do not need a headless browser to test it; you can invoke it directly in Vitest/Jest.
- **Two mandatory test categories**:
  1. **Input Schema Validation tests**: Pass malformed payloads, invalid emails, negative numbers, or SQL strings and assert that the action returns a structured validation error rather than throwing an uncaught 500 error.
  2. **DAL "Deny Tests" (Authorization boundaries)**:
     - Positive tests verify what an authorized user *can* do.
     - **Deny tests** explicitly verify that an authenticated user *cannot* access or mutate records belonging to a different tenant, user, or organization (Insecure Direct Object Reference / IDOR prevention).

```typescript
// serverActions.test.ts - Direct execution of Server Action with Deny Test
import { updateOrganizationName } from '@/actions/organization';
import { db } from '@/lib/db';

describe('updateOrganizationName Server Action', () => {
  it('rejects invalid inputs with descriptive error schema', async () => {
    const result = await updateOrganizationName({ orgId: 'org_123', name: '' });
    expect(result.success).toBe(false);
    expect(result.errors?.name).toContain('Organization name cannot be empty');
  });

  // ✅ Mandatory Deny Test: IDOR Protection
  it('denies mutation when authenticated user does not belong to the target organization', async () => {
    // Mock session as User B
    vi.mocked(auth).mockResolvedValue({ user: { id: 'user_b', orgId: 'org_b' } });

    // Attempt to update Org A's name
    const result = await updateOrganizationName({ orgId: 'org_a', name: 'Hacked Org' });

    expect(result.status).toBe(403);
    expect(result.error).toMatch(/unauthorized/i);

    // Verify database record was NOT mutated
    const originalOrg = await db.organization.findUnique({ where: { id: 'org_a' } });
    expect(originalOrg?.name).not.toBe('Hacked Org');
  });
});
```

### Question e8a5be53-56c8-4f64-9fa9-24ed4a73e75f

- How must **TanStack Query (React Query)** be configured in integration test wrappers, and what are the rules for testing cache invalidation and query retries?

### Answer

- **The Configuration Trap**: By default, TanStack Query retries failed queries 3 times with exponential backoff (`retry: 3`) and uses garbage collection timers. In tests, a simulated 500 error will cause the test to hang for several seconds while retrying, triggering CI timeouts.
- **Test-wrapper configuration rules**:
  1. Set `retry: false` so network errors fail immediately.
  2. Set `gcTime: 0` (or `cacheTime: 0`) and create a **fresh `QueryClient` instance per test** to prevent cache leaks across test cases.
- **What to test**:
  - Test the transition from loading skeleton to populated UI via `findBy*`.
  - Test mutation side-effects: verify that completing a mutation triggers cache invalidation and causes the list query to refetch updated data.

```tsx
// test-utils.tsx - Isolated QueryClient per test with zero retries
export function renderWithQueryClient(ui: React.ReactElement) {
  const queryClient = new QueryClient({
    defaultOptions: {
      queries: { retry: false, gcTime: 0 },
      mutations: { retry: false },
    },
  });

  return render(
    <QueryClientProvider client={queryClient}>
      {ui}
    </QueryClientProvider>
  );
}

// UserList.test.tsx - Testing mutation cache invalidation
it('invalidates user list and refetches when new user is added', async () => {
  renderWithQueryClient(<UserManager />);

  expect(await screen.findByText('Alice')).toBeVisible();

  // Trigger mutation
  await userEvent.type(screen.getByRole('textbox'), 'Bob');
  await userEvent.click(screen.getByRole('button', { name: /add/i }));

  // Assert TanStack Query refetched and rendered the updated cache
  expect(await screen.findByText('Bob')).toBeVisible();
});
```

### Question 5065e699-4edf-4bb6-aa5a-a8d6b26d6934

- Why do tests for **Zustand stores** frequently contaminate subsequent tests, and how do you enforce state isolation across test suites?

### Answer

- **The Module State Leak**:
  - Zustand stores live in module-level scope outside the React component lifecycle.
  - Unlike React component state which unmounts and garbage collects, Zustand store state persists across multiple test files unless explicitly reset.
  - If Test A mutates `useCartStore.getState().addItem()`, Test B will inherit that item, causing inexplicable test ordering dependencies.
- **The Enforcement Discipline**:
  - Export a reset function or store the initial state slice.
  - Register a `beforeEach()` or `afterEach()` hook that resets all Zustand stores to their initial state.

```typescript
// cartStore.ts
import { create } from 'zustand';

interface CartState {
  items: string[];
  addItem: (item: string) => void;
  reset: () => void;
}

const initialState = { items: [] };

export const useCartStore = create<CartState>((set) => ({
  ...initialState,
  addItem: (item) => set((s) => ({ items: [...s.items, item] })),
  reset: () => set(initialState),
}));

// setupTests.ts - Auto-reset store before each test runs
beforeEach(() => {
  useCartStore.getState().reset();
});
```
