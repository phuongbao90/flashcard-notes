# Coverage, Mutation & Measuring Test Quality

### Question 3846e5af-b4fb-4f3a-8683-7a9aeec5f779

- What is the honest purpose of **code coverage**, and why can high coverage metrics create a false sense of security while hiding completely untested software?

### Answer

- **What coverage is for**: Code coverage (lines, statements, branches) has only one honest capability: **finding code that was never executed during test runs**. It highlights blind spots in your test suite.
- **What coverage cannot do**: It can **never** certify that code is correct or tested.
  - A test can execute 1,000 lines of complex business logic with zero assertions (`expect(...)`), and coverage tools will happily report 100% test coverage.
  - Coverage measures execution path traversal, not the **validity of assertions**.
- **The danger of coverage targets**: When management mandates an arbitrary global target (e.g., "All code must have 85% coverage"), developers game the system by writing assertion-less "smoke" tests or asserting trivial getters rather than wrestling with hard edge cases.

```typescript
// ❌ 100% Line Coverage, 0% Correctness Assertion!
export function calculateOrderDiscount(order: Order): number {
  if (order.total > 100 && order.user.isVip) {
    return order.total * 0.2; // 20% discount
  }
  return 0;
}

// In test file:
it('processes discount function', () => {
  // Executes both lines! Coverage tool reports 100% statement and branch coverage!
  calculateOrderDiscount({ total: 150, user: { isVip: true } });
  calculateOrderDiscount({ total: 50, user: { isVip: false } });
  // Notice: ZERO ASSERTIONS! If the discount calculation changes to 99%, test stays green!
});
```

### Question f00b3e28-73cc-4a8a-b429-a861e585b116

- How does **Mutation Testing (Stryker)** measure the actual quality of test assertions, and what does it reveal that standard coverage metrics completely overlook?

### Answer

- **The Mutation Testing Mechanism**:
  1. **Mutant Generation**: The mutation testing tool (e.g. Stryker for JS/TS) intentionally introduces subtle syntactic bugs ("mutants") into your production code:
     - Changes `>` to `>=`.
     - Changes `a && b` to `a || b`.
     - Replaces function return values with `null` or `undefined`.
     - Removes method calls like `dispatch()` or `save()`.
  2. **Test Run**: Stryker runs your existing test suite against each mutant.
  3. **Evaluation**:
     - If your tests fail, the mutant is **killed** (your assertions correctly detected the bug).
     - If your tests still pass, the mutant **survived** (your tests failed to detect the bug).
- **The Mutation Score**: `Killed Mutants / Total Mutants * 100`.
- **The Differentiator**: It detects the "assertion-less test" and "weak expectation" failure modes. If an engineer asserts `expect(res).toBeDefined()` instead of `expect(res.discount).toBe(15)`, mutation testing catches that the mutant survived.

```typescript
// Original production code
function isEligibleForRefund(purchaseDaysAgo: number, isUsed: boolean): boolean {
  return purchaseDaysAgo <= 30 && !isUsed;
}

// 👾 Mutant 1 generated by Stryker:
// return purchaseDaysAgo < 30 && !isUsed;  (Boundary mutant)

// 👾 Mutant 2 generated by Stryker:
// return purchaseDaysAgo <= 30 || !isUsed;  (Logical operator mutant)

// If tests only checked purchaseDaysAgo = 10, Mutant 1 survives!
// Mutation testing forces developers to write boundary assertions (e.g. Day 30 vs Day 31).
```

### Question 2a450f6c-928c-40a3-b145-282e72e343cc

- How does the **Churn × Coverage Matrix** prioritize test engineering investments in a mature codebase?

### Answer

- **The ROI Dilemma**: In a 500,000-line legacy codebase, you cannot achieve high test coverage across every file. How do you decide where to write tests?
- **The 4 Quadrants of the Matrix**:
  - **High Churn / Low Coverage (Quadrant of High Risk)**: Files modified frequently (high git commit frequency, high bug incidence) that lack tests. Every new commit has a high probability of introducing undetected regressions. **Top priority for test investment.**
  - **High Churn / High Coverage (Quadrant of Value)**: Core business engines actively being enhanced. Existing tests protect against regressions; continue maintaining quality gates.
  - **Low Churn / Low Coverage (Quadrant of Benign Neglect)**: Stable legacy code that hasn't changed in 3 years and generates zero bug tickets. Do not waste sprint cycles retrofitting tests here.
  - **Low Churn / High Coverage (Quadrant of Overhead)**: Stable code with high test maintenance.

```
Commit Churn (Frequency of Change)
▲
│  [ HIGH RISK - PRIORITY 1 ]        [ VALUE PRESERVATION ]
│  Low coverage, high change rate    High coverage, high change rate
│  -> Write integration tests now!    -> Maintain fast CI execution
│
│  [ BENIGN NEGLECT ]                [ LOW VALUE / OVERHEAD ]
│  Low coverage, rarely changed      High coverage, rarely changed
│  -> Do NOT retrofit tests here     -> Avoid adding more tests
└─────────────────────────────────────────────────────────────► Test Coverage
```

### Question 8e214b22-443e-486c-a546-f429d6a19350

- What is the **Regression-Gated Bug Fixing discipline**, and why is it considered the highest-ROI testing habit in software engineering?

### Answer

- **The Golden Rule**: "Never fix a production bug without first writing an automated test that reproduces the bug and fails."
- **The 3-Step Protocol**:
  1. **Reproduce First (Red)**: Write a unit, integration, or E2E test that recreates the user's reported defect. The test **must fail** before any production code changes are made.
  2. **Implement the Fix (Green)**: Modify the minimal production code necessary to resolve the root cause. The test now turns green.
  3. **Permanently Prevent Recurrence (Refactor & Guard)**: The test is committed alongside the fix. It enters the permanent CI suite, mathematically guaranteeing that the exact same bug can never regress undetected.
- **Why it provides unmatched ROI**:
  - You write tests for code that has proven failure modes, rather than guessing what might break.
  - Over time, the test suite organically hardens around the actual, real-world vulnerabilities of your specific application.

```typescript
// bug-report-1042.test.ts - Regression test committed before the bug fix
it('[BUG-1042] applies coupon code case-insensitively', async () => {
  // Bug: User entered 'summer20' but DB coupon code was 'SUMMER20', throwing 400
  render(<CheckoutCouponForm />);
  const user = userEvent.setup();

  await user.type(screen.getByRole('textbox', { name: /coupon/i }), 'summer20');
  await user.click(screen.getByRole('button', { name: /apply/i }));

  // ✅ Red before fix (failed with 'Invalid coupon'); Green after fix
  expect(await screen.findByText(/discount applied: \$20 off/i)).toBeVisible();
});
```
